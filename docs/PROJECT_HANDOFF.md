# Project handoff

Checkpoint of the DoIC MUJ site so another device can clone it and continue.

Remote: `https://github.com/FrostXMello/isc-doic-muj-dashboard` (branch `main`). Pushes to `main` auto-deploy to the Vercel project `isc-doic-muj-dashboard` (https://isc-doic-muj-dashboard.vercel.app).

## Current state

Implemented:

- Official data: `src/lib/official/` holds the records imported from MUJ's Internationalization pages (reviewed 2026-09-30): 116 institutions, 132 collaboration rows, 39 countries, 7 regions, 6 programmes, 6 offerings, 4 calls, 17 documents, and 14 activities. Everything is `source-imported` or `needs-review`, never `verified`. The source-by-source audit, conflicts, and exclusions are in `docs/muj-internationalization-source-audit.md`.
- Public site: homepage with the globe, privacy, and terms. The student portal (`/student-portal`, sign-in required) has its own top nav over home, opportunities, partner directory (`/student-portal/partners`, `/student-portal/partners/[slug]`), programmes, and about. The old `/opportunities`, `/partners`, `/partners/[slug]`, `/programs`, `/about` URLs redirect (308) into the portal. It reads `src/lib/official/public.ts` and `src/lib/data.ts`, which expose no contacts, statuses, or dates. The 16 earlier-directory partner slugs redirect (307) to `/student-portal/partners` (`retiredPartnerSlugs` in `next.config.ts`).
- Internal Portal at `/internal`: dashboard, institutions, agreements (MoUs), programme offerings, opportunities, activities, documents, reports, settings. It reads through the repository layer in `src/lib/internal/data/`. Every detail page shows provenance (source link, last checked, verification), and institution and agreement pages have a nodal-contacts panel.
- Supabase backend: schema, RLS, storage bucket, seeds, and RLS tests in `supabase/` (see Backend), applied to the hosted project `oqmwrifysignwmgxiecd`. Official data, earlier directory names, and the internal contacts are loaded there.
- Authentication (see Authentication): one email + password sign-in at `/login` for both portals, role-based routing from `public.user_roles`, password reset, sign-out, account menus, and account and role management for DoIC admins in `/internal/settings`.

Not implemented, on purpose:

- Write actions (other than role grants), uploads, and application forms.
- Agreement dates or status: the official page does not publish them. DoIC must supply them from the signed documents.

## Backend (Supabase)

| Path | Contents |
| --- | --- |
| `supabase/config.toml` | Local stack config (`npx supabase start`) |
| `supabase/migrations/` | Schema, triggers, RLS policies, storage bucket + policies |
| `supabase/seeds/` | Seeds generated by `npm run db:seed:generate` from the TS data (see Seeds) |
| `supabase/private/` | Gitignored. Generated `muj-nodal-contacts.sql` (internal contacts) |
| `supabase/tests/database/rls.test.sql` | pgTAP RLS tests (`npx supabase test db`) |

**Roles** (`public.app_role`): `student`, `isc_team`, `doic_admin`, `leadership`. Grants live in `public.user_roles`; only `doic_admin` can write it, and an admin cannot remove their own admin role. Policies call SECURITY DEFINER helpers with a fixed `search_path`, kept in the `private` schema so they are not exposed as REST RPCs: `private.has_role()`, `has_any_role()`, `current_app_roles()`, `is_internal()`, `can_edit_internal()`, `is_doic_admin()`. `user_metadata` is never used for authorisation. A signup trigger creates the profile only; it grants no role (migration `20261001090000_admin_assigned_roles.sql`), so a DoIC admin decides every account's access.

**RLS** (enabled on every table):

- Public (anon + signed in): regions; countries/institutions where `is_public`; programmes/offerings where `is_published`; opportunities that are `published` and not sample data.
- Internal read (isc_team, doic_admin, leadership): everything above plus agreements, collaboration areas, documents, document links, activities, student profiles, applications.
- Writes: isc_team and doic_admin insert/update; deletes are doic_admin only. Leadership is read-only.
- Students: own profile (name only), own student profile, own applications (create for open published calls; no status changes), own notifications (mark read).
- `audit_logs`: written only by trigger; readable by doic_admin and leadership; no update/delete for any API role.

**Storage**: private bucket `institutional-documents` (25 MiB, PDF/Office/CSV/TXT/PNG/JPEG). Path `{entity_type}/{entity_uuid}/{filename}`, entity types `institutions|agreements|programs|program-availability|opportunities|activities|documents`. Read: internal roles. Upload/replace: isc_team, doic_admin. Delete: doic_admin.

**Official data tables** (migrations `20260930130000_official_enums.sql` and `20260930130100_official_provenance_contacts.sql`):

- Provenance columns on institutions, agreements, programmes, offerings, opportunities, documents, and activities: `source_url`, `source_title`, `source_last_checked`, `verification_status`. Agreements add `type_label` (the row's wording) and `source_section`; documents add `external_url` and `publicly_accessible`.
- `institution_contacts`: nodal contacts, one per agreement row where the page lists one.
  - Visibility is `internal` by default. `anon` has no grants.
  - Select is limited to internal roles. Insert and update are for editors; delete is admin-only.
  - Audit triggers are attached.
- `agreement_public_summaries`: agreement reference, listed name, type, and type wording, for public institutions only.
  - It is maintained by a SECURITY DEFINER trigger on `agreements`. Sample rows are excluded.
  - API roles have no writes.
  - This lets the public read agreement types without access to `agreements` itself.

**Seeds** (generated by `npm run db:seed:generate`; loaded locally by `supabase db reset`):

- `01_official.sql` contains the official data (`data_source='official'`) as idempotent upserts keyed on slug or code.
- `02_directory.sql` contains the 16 earlier directory names (`data_source='directory'`, `is_public=false`, `needs-review`).
- `03_sample.sql` contains fictional records (`data_source='sample'`), **local only**.
- `supabase/private/muj-nodal-contacts.sql` (gitignored) is written only when `data/private/muj-nodal-contacts.json` exists.

Never run `supabase db push --include-seed` against a hosted project; that would load the samples.

**Loading official data into hosted** (password from the Keychain; never print the connection string):

```bash
export SUPABASE_DB_PASSWORD="$(security find-generic-password -s doic-supabase-db -w)"
PGPASSWORD="$SUPABASE_DB_PASSWORD" PGSSLMODE=require psql "$(cat supabase/.temp/pooler-url)" \
  -v ON_ERROR_STOP=1 -1 -f supabase/seeds/01_official.sql -f supabase/seeds/02_directory.sql \
  -f supabase/private/muj-nodal-contacts.sql
```

`-1` wraps the load in one transaction. Re-running it is safe because the seeds are upserts.

**App integration**: `src/lib/internal/data/context.ts` picks the dataset per request.

- `INTERNAL_DATA_SOURCE=supabase` + `NEXT_PUBLIC_SUPABASE_URL` + `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (what Vercel uses, production and preview): reads Supabase as the signed-in user via `@supabase/ssr` (`src/lib/supabase/server.ts`). Rows map to the existing types using `slug`/`code` as ids, so URLs, filters, statuses, and reports are unchanged. `institution_contacts` is queried only when the user holds an internal role in `user_roles`, and RLS applies the same rule.
- `INTERNAL_DATA_SOURCE=static` (the local default): the official dataset from `src/lib/official/`, no env vars needed. Contacts are never available; the contacts panel reads "Restricted — available to signed-in DoIC staff".
- Both sources pass through `canonicalDataset()` (`src/lib/internal/data/dataset.ts`), which orders every entity by id (programmes keep their curated order), so lists and panels render identically whichever source is active. On 2026-10-01 every internal list, filter, sort, and detail page (339 URLs) rendered the same text in both modes, apart from the contacts panels.
- `INTERNAL_SAMPLE_DATA=true` mixes the fictional sample records into either source. Off by default, and ignored when `VERCEL_ENV=production`.
- Write actions (create, edit, upload) are placeholders, rendered through `RecordAction` only for roles that `roleAllows()` (`src/lib/internal/permissions.ts`): Leadership sees a read-only portal; isc_team and doic_admin see the placeholders. RLS remains the real boundary.
- If Supabase Auth is unreachable, `src/proxy.ts` and `getAuthContext()` send portal visitors to `/login?notice=unavailable` instead of treating them as signed out.
- `src/proxy.ts` refreshes the Supabase session and gates both portals regardless of `INTERNAL_DATA_SOURCE` (see Authentication).
- `SUPABASE_SECRET_KEY` (server-only, never `NEXT_PUBLIC_`) is read only by `src/lib/supabase/admin.ts`, and used only for the Auth Admin API inside the doic_admin account-management server actions. Every data read and write runs as the signed-in user under RLS.

**First admin** (the hosted project has no accounts yet):

1. Dashboard → Authentication → Users → Add user → Create new user, with the admin's email, a strong password, and "Auto Confirm User" ticked.
2. In the SQL editor:

```sql
insert into public.user_roles (user_id, role)
```

## Authentication

- `/login` is the only sign-in page. Server actions in `src/lib/auth/actions.ts` handle sign-in, sign-out, reset requests, and password updates; no secret reaches the client.
- Roles are read from `public.user_roles` for the user returned by `auth.getUser()` (`src/lib/auth/session.ts`, `src/lib/auth/roles.ts`). Priority: `doic_admin` > `isc_team` > `leadership` > `student`.
- Landing: any internal role → `/internal`; only `student` → `/student-portal`; no role → `/access-pending`. A `next` parameter is honoured only when it is a same-origin path the user's roles allow (`src/lib/auth/next-path.ts`).
- Enforcement runs twice: `src/proxy.ts` (session refresh + redirects on `/internal`, `/student-portal`, and the auth pages) and the portal layouts (`requirePortalAccess`). Signed-out visitors go to `/login?next=…`; students who open `/internal` see `/unauthorized`; internal roles may use both portals.
- Password reset: `/forgot-password` (always answers generically) → email link → `/auth/callback` (PKCE code or `token_hash`) → `/reset-password`. Expired or reused links return to `/forgot-password` with a notice.
- Role management: `/internal/settings` → Portal access, visible to `doic_admin` only. Changes go through the admin's own session, so RLS is the authority; an admin cannot remove their own `doic_admin` role (also enforced in the update policy).
- Account management (`doic_admin` only): create account (email, password of 12+ characters, any roles), set a user's password, delete a user. Each server action re-checks `doic_admin` via `getUser()` + `user_roles` before calling the Admin API; role grants still go through RLS. Admins cannot reset or delete their own account here. Without `SUPABASE_SECRET_KEY` the section reads "Account creation unavailable".

## Constraints

- Do not invent institutional data. Never infer agreement status, dates, eligibility, fees, deadlines, or contacts. Keep agreement types as each row states them; a listing is not an MoU. Official imports stay `source-imported` until DoIC confirms them against signed documents.
- This repository is public. Contacts live only in gitignored `data/private/` and `supabase/private/`, and in the RLS-protected table. Never render them on public pages or pass them to client components.
- The International Student Cell student list is excluded: it is not authoritative and is not imported.
- Coordinates are the country pin, not campus locations.
- Run `npm run data:check` after editing `src/lib/official/`.
- Keep institutions, agreements, programmes, and programme availability as separate tables. Do not generate availability as a cross-product.
- RLS is the security boundary. The secret key is limited to Auth Admin calls in doic_admin account management; do not use it for data reads or writes.

## Device handoff

```bash
git clone https://github.com/FrostXMello/isc-doic-muj-dashboard.git
cd isc-doic-muj-dashboard
npm install
npm run dev
```

The public pages need no environment variables; the portals need `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` for sign-in. The private contacts JSON is not in git; copy `data/private/muj-nodal-contacts.json` from a trusted device if you need to regenerate the contacts SQL. To work against a local database (needs Docker): `npx supabase start`, then `npx supabase db reset` (migrations + seeds) and `npx supabase test db`. Copy `.env.example` to `.env.local` for Supabase settings; never commit real values.
